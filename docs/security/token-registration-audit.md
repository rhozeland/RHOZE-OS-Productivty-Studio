# Token Registration and Approval Audit

> **Status: Work in progress.** This is a static repository audit prepared for engineering review. Task #155 is not marked complete. No live database or deployed environment was inspected, so migration-derived behavior has not been runtime verified.

## 1. Purpose and Scope

### US #154 — Prevent fraudulent token registration

**Story:** As a creator, I want Rhoze to verify that I control a token's creator wallet before linking the token to my profile, so that another user cannot reserve or claim my mint and unverified tokens cannot be presented as approved.

The supplied acceptance criteria are the source of truth:

1. Server-verified creator-wallet ownership and signed challenge proof are required before approving a profile token or `creator_tokens` row.
2. The server validates the mint and retrieves its creator wallet from a trusted source.
3. Pending submissions cannot reserve a mint.
4. Verification applies to profile creation, updates, and every registration path.
5. Direct client writes cannot bypass approval enforcement.
6. Unverified tokens remain pending or are rejected and are never presented or used as approved.
7. Only one creator account can claim a mint, including during concurrent registration attempts.
8. Retrying verification for the same account and mint is idempotent.
9. Legitimate creators can successfully register their tokens.
10. Invalid mints, mismatched wallets, expired or reused challenges, and failed verification cannot create approved claims.
11. Errors communicate the failure reason and retry guidance where appropriate.

### Task #155 — Audit token registration and approval paths

**Definition of done:** Every registration and approval path is documented, and the intended verification and uniqueness rules are agreed upon. This revision records the agreed `creator_tokens` authority direction and intended security rules. The document remains a work in progress and Task #155 is not declared complete here; no runtime behavior is claimed as verified.

The review is limited to repository source and migration history. It does not establish which migrations have been applied to any deployed database, inspect production data, or prove behavior under live Supabase/Postgres roles.

## 2. Current Architecture

### Profile token registration

`profiles` stores a live token pair (`token_mint_address`, `token_ticker`) and a separate pending pair with submission status/review metadata. `SettingsPage` writes the live pair through Supabase/PostgREST. The latest `BEFORE UPDATE` trigger on `profiles` routes a non-empty live-pair change by a non-admin/non-service caller into pending fields and preserves the old live pair. Clearing both live fields resets the submission state. Direct changes to review-state fields are rejected. The status describes the pending/recent submission; during a replacement, it can be `pending` or `rejected` while the old live mint remains in the live fields. The trigger is defined only for `UPDATE`, not `INSERT` (`20261108000000_enforce_token_approval_reject_unauthorized.sql:59`, `:77`, `:127`; rejection leaves live fields alone at `20261104000000_remove_strict_flag_from_review_token_submission.sql:160`).

### `creator_tokens` registration

`public.creator_tokens` is a multi-token table. Authenticated users can insert their own pending rows and update their own pending rows through direct table access. This repository search found no production UI or Edge Function that inserts or reviews this table; direct PostgREST access remains a database-supported entry path. Administrators can review via `review_creator_token` or update rows under the admin RLS policy. Each row records owner UUID, mint, ticker/name, primary flag, status, and approval/rejection metadata.

### External mint attachment

External mint attachment is a distinct Project/Work workflow. A signed, short-lived challenge is bound to the authenticated user, target, mint, and creator wallet. The Edge Function validates the target and mint details, verifies the wallet signature, and calls a service-only database RPC. A database guard prevents ordinary Project/Work writes from changing protected external-mint fields. This flow attaches a mint to a Project or Work; it does not create or approve a profile submission or `creator_tokens` row.

### Relationships and synchronization

`profiles` and `creator_tokens` contain overlapping mint/ticker data but have separate write and approval paths. A one-time migration backfilled eligible profile live mints into approved primary `creator_tokens` rows. An `AFTER INSERT OR UPDATE OR DELETE` trigger mirrors a primary approved `creator_tokens` row to the profile compatibility fields. Profile review does not create or update a `creator_tokens` row. The mirror is conditional and does not synchronize all state transitions, so the two records can diverge. In the current implementation, neither record persists creator-wallet proof; the agreed target authority is `creator_tokens` as described in Sections 6 and 8.

The mirror's interaction with the latest profile approval trigger is partially compatible by code path: `mirror_primary_token_to_profile` is `SECURITY DEFINER`; its profile `UPDATE` reaches `enforce_token_approval`, whose admin, service-role, and maintenance branches return the proposed row unchanged. That allows a trusted CT review/update to mirror live mint fields instead of re-queueing them (`20260530064402_30569342-2f47-40ca-a5a4-602c3536c120.sql:82`, `:99`, `:100`; `20261108000000_enforce_token_approval_reject_unauthorized.sql:34`, `:38`, `:42`, `:55`). However, the mirror changes only `token_mint_address` and `token_ticker`; it does not set profile `token_submission_status` or review metadata. If an approved primary CT row is rejected or made non-primary, the trigger has no corresponding `ELSE` branch to clear or demote the profile fields. Thus, the two triggers do not create a complete or status-consistent mirror. This is a static control-flow finding; deployed trigger execution has not been tested.

### Migration sequence affecting effective profile behavior

The initial profile approval trigger/RPC and state columns were added in `20260527224622_2947817b-6d72-4c5b-918d-4aa6c003f305.sql`. `20261027034058_bind_token_approval_to_submission.sql` bound review to expected submitted values but exposed a `_strict` option; `20261030205236_enforce_strict_token_approval_validation.sql` made strict validation the default while retaining that option. `20261104000000_remove_strict_flag_from_review_token_submission.sql` drops the bypass-capable signature and makes expected-value checks unconditional. The latest profile trigger replacement found is `20261108000000_enforce_token_approval_reject_unauthorized.sql`; it replaces earlier trigger behavior and explicitly rejects unauthorized review-state edits.

## 4. Existing Security Protections

- **Profile approval trigger:** On `UPDATE`, ordinary callers cannot directly set review-state columns. A live token change is converted to a pending submission; clearing the live pair resets state. The latest trigger has explicit admin, service-role HTTP, and canonical maintenance-session branches. No matching `BEFORE INSERT` token-approval trigger was found.
- **Profile admin review safeguards:** The profile review RPC is admin-only, locks the profile row, requires the current status to be pending, and compares the exact pending mint, ticker, and submission time to the queue snapshot. The latest migration removes an earlier optional strictness bypass.
- **Admin UI safeguards:** `AdminPage` checks admin status before showing administrative content. The profile submission UI invokes the snapshot-bound RPC. These UI checks complement, but do not replace, database authorization.
- **RLS and grants:** Profile INSERT/UPDATE are granted to authenticated users, with row scope constrained by own `user_id`; service role has broad access. `creator_tokens` allows authenticated SELECT/INSERT/UPDATE, with owner pending-only insert/update policies and an admin update policy. No authenticated delete grant/policy was found for `creator_tokens`; service role has all privileges. These are migration-derived permissions and need deployed-role verification.
- **Signed wallet challenge for attachment:** Challenge rows are service-role-only. The challenge is stored server-side and bound to caller, target, mint, and creator wallet; signature verification checks the exact stored message and wallet. Expiry/use is checked in the database RPC, with a later migration refreshing expiry after locking. This is the clearest reusable ownership-proof pattern found, but its persisted result authorizes Project/Work attachment only.
- **Existing account-wallet binding:** `WalletButton` stores the connected public key in `profiles.wallet_address` and sets `wallet_locked`; later wallet changes use an admin-reviewed `wallet_change_requests` flow. The initial bind does not sign a server-issued challenge, and profile token registration does not compare the registered mint’s creator wallet with this field. (`src/components/WalletButton.tsx:35`; `supabase/migrations/20260414033429_7e2d8228-cac7-45ef-bc7d-c24cbb4edc24.sql:5`, `:45`.)
- **Separate holder verification:** `verify-token-grant` accepts a signed user message and verifies token balance for a time-limited holder grant. This proves a holder-side condition for access; it does not prove that the caller owns a mint’s creator wallet or authorize registration (`src/components/profile/TokenGateConnectSheet.tsx:63`, `:67`; `supabase/functions/verify-token-grant/index.ts:78`, `:91`, `:118`).
- **Token attachment database enforcement:** A trigger guards Project/Work token-field changes, and approved-token links use a database helper that checks token owner and approved status. The latest `enforce_project_work_token_linking` migration preserves trusted token metadata for verified paths.
- **Mint uniqueness:** `creator_tokens.mint_address` is globally unique within that table; a partial unique index permits only one primary row per `user_id`. These rules do not span `profiles`, pending profile fields, or external attachment challenges.

## 5. Identified Security Gaps

Labels below distinguish code facts from conditions whose practical exploitability depends on data, grants, deployment, or caller state.

### Confirmed static-analysis findings

- **Registration lacks creator-wallet proof:** Neither the Settings profile submission nor direct `creator_tokens` insertion verifies control of the token’s creator wallet. The profile approval RPC and `review_creator_token` also do not perform that verification. No `verify-artist-mint-ownership` symbol or path was found in this checkout.
- **Registration lacks mint validation:** The profile and `creator_tokens` registration/review paths do not perform the Solana account and pump.fun metadata checks present in the external attachment Edge Function.
- **Uniqueness differs by record:** `profiles.token_mint_address` has a non-unique index. `creator_tokens.mint_address` is unique only within `creator_tokens`. There is no cross-table constraint or shared claim mechanism.
- **Pending `creator_tokens` row reserves a mint:** The global unique constraint includes pending rows, so one pending submission prevents another `creator_tokens` insert for the same mint until the first row is changed or removed.
- **Pending-row approval metadata is client-writable:** Table-wide authenticated INSERT/UPDATE grants and the owner RLS checks allow a caller to supply or update `approved_at` and `approved_by` on an own row while keeping `status='pending'`; no CT trigger protects these fields. Static call-site search found no product consumer of these metadata fields, so this does not itself prove an approval bypass. It does make the metadata unreliable as evidence of approval or review (`20260530064402_30569342-2f47-40ca-a5a4-602c3536c120.sql:21`, `:31`, `:32`, `:54`, `:60`, `:64`, `:75`).
- **Profile review and creator-token review are separate:** `review_token_submission` updates only `profiles`; `review_creator_token` updates only `creator_tokens`. No transaction-level synchronization between these reviews is defined.
- **Approved CT rows do not promote profile approval state:** The mirror writes only profile mint/ticker fields. In the migration sequence, profile token fields were first backfilled from `coin_launches` (`20260521081704_f74bff92-89e3-4469-a9cf-1f97872811a0.sql:14`); `token_submission_status` was later added with default `none` (`20260527224622_2947817b-6d72-4c5b-918d-4aa6c003f305.sql:7`, `:9`); then CT rows were backfilled as `approved` (`20260530064402_30569342-2f47-40ca-a5a4-602c3536c120.sql:117`, `:124`, `:125`). The mirror's same-value profile update does not change that status. This can leave an approved CT record paired with a profile mint whose status is still `none`; profile status-gated token-gating paths may reject it while discovery consumers still show it. This describes migration logic, not the deployed row population.
- **Creator-token review is not snapshot-bound:** The RPC accepts token ID, decision, and reason, and updates the row currently identified by that ID. It does not require pending status or compare the current mint/metadata with the queue snapshot. Because owners may edit pending rows, a stale review action could apply to changed row contents; the actual UI timing and operational likelihood are not established here.
- **Mirror coverage is partial:** The mirror trigger copies mint/ticker only when a row is primary and approved and clears those fields on deletion of an approved primary row. Other changes do not provide general bidirectional synchronization.
- **CT rejection/demotion can leave a profile claim live:** `review_creator_token` can apply `rejected` to a row without requiring it to be pending. The mirror trigger only handles `NEW.is_primary AND NEW.status = 'approved'` and approved-row deletion; it does nothing on a status change to rejected or on demotion from primary. If that row was the profile's mirrored primary, profile live fields and its old status can remain. Profile-based consumers can then continue to display/use that profile mint, including status-gated consumers when the stale profile status is still `approved` (`20260530064402_30569342-2f47-40ca-a5a4-602c3536c120.sql:89`, `:99`, `supabase/migrations/20261104000000_remove_strict_flag_from_review_token_submission.sql:157`, `:160`; `src/components/profile/SupportFlowSheet.tsx:148`; `supabase/functions/verify-token-grant/index.ts:111`, `:114`). The linked Project record can also remain, and Roadmap Copilot's CT lookup does not re-check status (`supabase/functions/roadmap-copilot/index.ts:60`).
- **Public profile-token view does not itself filter approval status:** `creator_tokens_public` is built from profile token fields and filters visibility/ban conditions, but neither the view nor its public profile SELECT policy requires `token_submission_status = 'approved'` (`supabase/migrations/20260604043808_be600ce0-130c-4c41-9a5b-539a881ac443.sql:7`, `:23`, `:34`, `:38`). Exposure depends on which token-bearing profile row exists and how consumers use the view.

### Conditional security risks

- **Profile INSERT approval bypass:** The latest approval trigger is `BEFORE UPDATE` only. Profile INSERT is granted to authenticated users and its RLS check constrains `user_id`, not token fields. If a user can create a profile row through direct API insertion (for example, when the normal signup-created row is absent), the insert path has no token-specific approval trigger; inserted live token values and `token_submission_status='approved'` could avoid the update-based queue. The status check permits `approved` (`20260527224622_2947817b-6d72-4c5b-918d-4aa6c003f305.sql:9`, `:10`). Normal signup creates a profile without token fields, so the risk depends on the missing-profile condition and the effective column grants/policies.
- **Administrative approval without verified ownership:** Current approval controls ensure that an administrator performs the decision, not that the applicant controls the token’s creator wallet. Whether administrators independently verify ownership outside the application is not represented in these code paths.
- **Profile wallet fields are not creator proof:** The separately stored `profiles.wallet_address` and `wallet_locked` fields are not consulted by either token-registration path. A locked account wallet therefore does not establish ownership of a submitted mint’s creator wallet.
- **Pending mint reservation:** The pending-row uniqueness behavior may allow a claimant to hold a mint in `creator_tokens` and block another account’s submission. Static inspection confirms the constraint behavior; whether this can be exploited with a fraudulent claim depends on the actual access and review lifecycle.
- **Conditional promotion of simulated launch addresses:** If the historical `coin_launches.creator_id = profiles.id` backfill join matched a profile, the generated vanity `coin_launches.mint_address` (which is not created or validated as a Solana mint) could be copied into profile token fields and then included in the later profile-to-CT backfill as `approved`. The migration chain and address generator support this conditional path (`20260502015543_d4c3810b-461a-4310-862a-3c44e732dad8.sql:12`, `:54`; `20260521081704_f74bff92-89e3-4469-a9cf-1f97872811a0.sql:15`, `:27`; `20260530064402_30569342-2f47-40ca-a5a4-602c3536c120.sql:117`). No database rows were inspected, so this does not establish that any such profile or approved CT row exists.
- **Profile/creator-token mismatch:** A profile can have an approved live mint without a corresponding CT row, and CT state changes may not update all profile fields/state. The exact resulting user-visible state depends on which table each feature reads and whether the mirror update succeeds with the deployed trigger/role configuration.
- **Orphaned creator-token rows after account deletion:** Profile rows cascade from Auth deletion, but the CT schema declares no `user_id` foreign key and the account deletion function does not show CT cleanup. Whether service-side cleanup exists outside this repository is unverified.
- **Profile token visibility:** Because the public view does not filter approval status, a profile row containing a live mint may be exposed regardless of its submission state if it passes the view’s other filters. Consumer impact depends on view access and application handling.

## 7. Agreed Security Rules and Task Alignment

The following are intended rules for US #154 implementation, recorded as agreed direction in this task. They describe target invariants, not current behavior. No implementation or runtime verification is claimed.

### Intended security rules

1. **Proof before approval:** Every approved mint claim must have server-verified proof that the authenticated account controls the creator wallet returned for that valid mint by a trusted source.
2. **Profiles are a projection:** Profile token fields do not independently establish an approved mint claim. They project the approved primary `creator_tokens` row.
3. **Pending/rejected do not reserve:** Pending and rejected submissions do not participate in global mint uniqueness and cannot block another account from submitting or approving a claim.
4. **Atomic approved-claim uniqueness:** Database-level uniqueness allows at most one account to successfully approve a claim for a mint, including concurrent attempts.
5. **Idempotent retries without replay:** Repeating registration for the same account and mint is idempotent, but an expired or consumed challenge is never accepted again.
6. **Protected writes are server controlled:** Direct client writes cannot set approval state, approval metadata, verification metadata, or approved token ownership.
7. **Bound challenges:** A registration challenge is purpose-specific, expiring, single-use, and bound to the authenticated account, mint, and trusted creator-wallet identity.
8. **Safe profile projection:** Profile consumers do not expose unverified claims or retain stale approved token data after relevant state transitions. A current approved token remains distinguishable from a pending replacement.
9. **Preserve attachment contracts:** Preserve existing Project/Work attachment security and `creator_tokens` record identities where possible.
10. **Fail closed:** Missing or failed trusted-source validation cannot result in an approved claim.

### Task invariants, verification strategy, dependencies, and regression risks

The supplied Scrum titles and US #154 criteria are used below. Verification items are proposed coverage for the task, not tests executed by this audit.

#### #156 — Require server-verified creator-wallet proof

- **Invariant:** An approval path can rely only on server validation of the mint, trusted creator-wallet lookup, and a valid signed challenge bound to account, mint, and that wallet. Source failure, invalid mint, wallet mismatch, expiry, or replay cannot approve a claim.
- **Verification strategy:** Cover valid proof; invalid/unsupported mint; trusted-source missing, stale, or failed response; wrong signer; wrong account/mint/wallet binding; expired challenge; and consumed-challenge replay. Confirm failures leave no approved claim and provide a reason/retry signal where retry is appropriate.
- **Dependencies:** Select and document the trusted mint source, verifier boundary, challenge message/lifecycle, and server-controlled proof result. This is a prerequisite for secure promotion in #157 and #159.
- **Regression risks:** RPC/source outages may block legitimate registrations; unsupported wallet/address formats may cause false rejection. The existing external attachment verifier is target-bound and is only a reference pattern until reuse is demonstrated.
- **US #154 criteria:** 1, 2, 4, 9, 10, 11.

#### #157 — Enforce approval rules on profile inserts and updates

- **Invariant:** Profile `INSERT` and `UPDATE` cannot independently create or expose an approved claim. Only a corresponding approved CT claim can populate the profile projection; direct clients cannot write protected approval or verification fields.
- **Verification strategy:** Exercise signup and missing-profile insert paths, ordinary profile updates, token replacement, direct attempts to set live/pending/status/reviewer fields, admin review, CT mirror updates, and projection changes after approval/rejection. Assert profile fields remain consistent with the approved primary CT row and a pending replacement does not overwrite the current approved value.
- **Dependencies:** #156 proof result and the agreed CT authority/projection contract; enumerate all profile readers that use live token fields.
- **Regression risks:** Signup and Settings profile fallback can break if inserts become too restrictive. Discovery and holder-gating consumers read profile fields directly, and the latest trigger currently protects updates only.
- **US #154 criteria:** 4, 5, 6, 8.

#### #158 — Prevent pending submissions from reserving a mint

- **Invariant:** Pending and rejected CT rows are non-reserving; one account's pending row cannot prevent another account from submitting the same mint.
- **Verification strategy:** Submit the same mint as multiple accounts while all rows are pending; reject one and retry; confirm neither pending nor rejected rows are treated as approved or returned by approved-token consumers.
- **Dependencies and sequencing:** Define pending/rejected lifecycle and coordinate with #159. Do not relax or remove the current all-status `UNIQUE (mint_address)` until the approved-claim uniqueness enforcement is active; there must be no schema/deployment interval in which concurrent approvals can create multiple approved rows for one mint.
- **Regression risks:** Existing code assumes globally unique CT mints, and rows/attachments may depend on stable CT IDs. Changing uniqueness must preserve pending-row editing, review, and attachment eligibility.
- **US #154 criteria:** 3.

#### #159 — Enforce one approved creator claim per mint

- **Invariant:** The database permits at most one approved CT claim per mint across accounts under concurrent attempts; the same account/mint retry resolves idempotently. Profile fields are a projection and cannot establish a second claim.
- **Verification strategy:** Race two verified accounts attempting approval for one mint; assert one approved row and one non-approved outcome. Verify the #158-to-#159 schema transition never exposes an interval where multiple approved rows can be committed. Retry for the same account/mint and assert a stable claim identity/result without reusing a consumed challenge. Check profile projection and existing Project/Work CT-ID links through approve, reject, primary change, and replacement transitions.
- **Dependencies:** #156 proof boundary, #158 non-reserving pending state, the `creator_tokens` authority direction, and a defined approval/review lifecycle. Approved-only uniqueness must be enforceable before pending duplicates are permitted.
- **Regression risks:** The current global unique constraint includes pending rows, while profile live mints are not unique. Consumers depend on stable CT IDs and approved status; mirror behavior currently does not clear profile fields when an approved primary row is rejected or demoted.
- **US #154 criteria:** 3, 7, 8.

#### #160 — Add registration security tests

- **Invariant:** Automated coverage protects the end-to-end rules across every registration path and database boundary; no route can create an unverified approved claim or expose stale projected data.
- **Verification strategy:** Add integration coverage for #156–159, including profile inserts/updates, direct CT writes and protected metadata, missing trusted-source responses, wallet mismatch, expiry/replay, same-account idempotency, cross-account concurrent approval, pending non-reservation, and projection transitions. Include regression checks for Project/Work attachment protections and CT identity preservation.
- **Dependencies:** Stable APIs/schema, test fixtures for the trusted-source verifier, concurrency-capable database tests, and explicit product decisions that affect expected approval/lifecycle results.
- **Regression risks:** Tests tied to migration setup or remote RPC behavior may be flaky; tests must distinguish verification from any separate manual review gate. Existing profile approval and external attachment tests do not substitute for registration-specific coverage.
- **US #154 criteria:** 1–11.

## 8. Authority Options and Agreed Architectural Direction

The repository currently has two partially overlapping records and no record that stores creator-wallet proof. The options below are assessed against the supplied US #154 rules. **Team-approved for Task #155:** option B as the authority direction, with the security rules in Section 7. **Not approved here:** detailed schema, API, migration, or rollout choices. Options A and C remain comparison alternatives; Section 9 lists unresolved product requirements.

### A. `profiles`

- **Compatibility:** Best immediate fit for the many profile, discovery, support, and holder-gating readers. It represents one mint per creator, not the multi-token registry used elsewhere.
- **Database enforcement:** A database rule could make each non-null live profile mint unique across creators while leaving separate pending fields outside that constraint. Current `idx_profiles_token_mint` is non-unique, and pending profile fields have no mint uniqueness. A partial constraint keyed only to `token_submission_status='approved'` would be ambiguous during replacement because that status can describe a new pending/rejected submission while the old live mint remains. A database boundary would still be needed to accept only server-verified proof before setting approved/live state; current RLS and update trigger do not cover the profile INSERT path.
- **Consumers:** Existing profile readers and `creator_tokens_public` would remain direct. Project/Work attachment still depends on CT IDs and status, so a profile-authoritative claim must be copied into CT or resolved through an adapter.
- **Concurrency and idempotency:** A unique constraint over non-null live profile mints could serialize competing live claims, but current profile rows can independently hold the same mint. Repeated submission for one account maps naturally to its single profile row, but the two-field live/pending state and challenge replay/idempotency still need an explicit registration operation.
- **Synchronization:** High ongoing requirement: maintain profile state and CT identity/status together. The existing mirror only syncs selected CT-to-profile mint/ticker fields; profile review does not sync back to CT.
- **Existing approvals:** A profile backfill from `coin_launches` without proof was attempted using the conditional `creator_id = profiles.id` join described above. CT was later backfilled from qualifying profile values as approved. Existing duplicates/conflicts and provenance would need review.
- **Complexity/regression:** Low impact to legacy profile readers, but weak fit to multi-token and Project/Work relationships; risks making the already split source-of-truth problem worse.

### B. `creator_tokens`

- **Compatibility:** Best fit for the existing multi-token registry, explicit owner/status fields, primary-token concept, and Project/Work link-by-ID design. It is already read by approved-token pickers, profile Bento, and Project/Work token cards.
- **Database enforcement:** The current table has a global unique `mint_address`, which enforces at-most-one row concurrently but also lets pending submissions reserve the mint. An approved-only uniqueness rule could enforce one approved claim atomically while allowing pending duplicates. A trusted server boundary must validate the mint and creator wallet and be the only path that promotes a claim; RLS alone does not establish cryptographic ownership.
- **Consumers:** Project/Work attachment needs little conceptual change because it already checks the CT owner and approved status. Profile displays, token gates, and `creator_tokens_public` still read profile fields, so the profile remains a compatibility projection (especially its selected primary token) and must carry a status consistent with the verified CT row.
- **Concurrency and idempotency:** A database uniqueness rule scoped to approved claims can arbitrate concurrent approvals. The current all-status unique constraint prevents a second pending submission, even by another account; current insert behavior also does not make a same-account retry idempotent. Idempotency must be defined for `(account, mint)` separately from global approved-claim uniqueness.
- **Synchronization:** Requires one-way approved-primary projection into profile fields and explicit behavior for approval, rejection, demotion, primary replacement, unlink, and deletion. The existing mirror is not sufficient as-is: it does not update profile approval metadata and can leave stale profile values after rejection/demotion.
- **Existing approvals:** This avoids creating a third registry, but existing CT approved rows include a profile backfill with no recorded proof. Their approval status cannot be treated as proof evidence based on current schema/history alone.
- **Complexity/regression:** Moderate. It requires changing registration entry paths and the pending/global-unique behavior, plus making the existing mirror/status contract reliable. It best fits current Project/Work attachments while retaining existing profile-facing APIs.

### C. Separate dedicated mint-claim table

- **Compatibility:** Provides a clean place for claim owner, mint, trusted creator wallet, proof/verification state, challenge reference, and approval lifecycle. It does not match current readers directly: profile consumers and CT-based attachment consumers would both need projections or lookups.
- **Database enforcement:** Can express pending versus verified/approved claim states and an approved-only unique mint constraint. A trusted verification boundary is still required; a table alone cannot validate a wallet signature or decide that an external creator-wallet source is trustworthy.
- **Consumers:** Requires a new integration with `profiles` for display/gating and `creator_tokens` for Project/Work links, or changes to those consumers. `creator_tokens_public` is currently profile-backed and would also need a projection or query-contract change.
- **Concurrency and idempotency:** A partial unique constraint can serialize approved claims while leaving pending claims non-reserving. A per-account/mint idempotency key can support retries. It is the clearest isolated claim model but creates a third stateful record to coordinate.
- **Synchronization:** Highest requirement if profile and CT remain consumer-facing; needs reliable projections and clear handling of state changes in all three tables.
- **Existing approvals:** Requires reconciling both profile and CT records into a new table, including collisions and rows with no persisted wallet-proof evidence.
- **Complexity/regression:** Highest. It gives the cleanest domain separation but adds schema, migration/reconciliation, write paths, permissions, tests, and projection risk without a demonstrated need for a third table in the current architecture.

### Agreed architectural direction — B. `creator_tokens` as claim record

**Agreed direction:** Use `creator_tokens` as the authoritative record for verified creator-mint claims, and retain `profiles.token_mint_address`/`token_ticker` as a compatibility projection for the selected primary approved token. Keep external Project/Work attachment as its separate workflow; its signed challenge can inform the verification design but its Project/Work attachment result is not a profile claim. Route every profile and CT registration/approval path through a server-verified mint/creator-wallet proof boundary. Pending submissions should not participate in global claim uniqueness or be published/used as approved. The database should arbitrate uniqueness among approved claims, including concurrent attempts, and registration retries for the same account/mint should resolve idempotently without challenge reuse. The projection must distinguish the current approved token from a pending replacement and must clear or update stale data after relevant state transitions. Preserve existing Project/Work attachment security and CT row identities where possible. Whether manual review remains as an additional approval gate is unresolved; proof is required before any approval either way.

This is the smallest architectural change in this comparison because it reuses the existing multi-token record and attachment foreign keys rather than introducing a third authority. It is not a small code patch: the profile registration entry point, client-write boundaries, CT pending uniqueness, approval transition, and mirror/status behavior all need to align. Existing discovery and token-gating consumers make profile projection compatibility a material constraint. This agreed direction does not prescribe detailed schema/API changes or resolve legacy-token, deletion, or US #8 decisions.
